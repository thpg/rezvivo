# REZVIVO: кэш 3D-тайлов O3DTBIN1

Это **бинарные массивы с независимым сжатием разделов**, не XML или JSON в архиве.
Расширение `.o3dt`. Формат реализован в `Osm3d/Osm3dTileBinary.pas`.
Файлы размещаются в `o3dt/v3/<generator hash>/PX<edge>Z<zoom>/.../<quadkey>.o3dt`.
Географическая сетка и ключ версии генератора остались прежними.

## Использование и совместимость

По умолчанию игра и OSM3D Studio записывают сжатый бинарный кэш. Старый X3D
читается автоматически. После успешной загрузки старый тайл переводится в бинарный
на рабочем потоке. Только после атомарной публикации нового файла удаляются
соответствующие `.x3d` и `.x3d.roads`. При ошибке конвертации исходник остаётся.
Полной конвертации всего кэша при запуске нет. Авторские X3D в Dream World —
ресурсы мира, эта миграция кэша их не изменяет.

Общая настройка игры и студии — `tile-cache-format.cfg` в **корне кэша**, одна
строка: `binary` (по умолчанию) или `x3d`. Применяется при следующем создании
карты; для однозначной проверки перезапустите приложение. Запись другим форматом
заменяет старый файл этого тайла. Чтение поддерживает оба формата в любом режиме.
Для временного теста переменная окружения `REZVIVO_TILE_CACHE_FORMAT` имеет приоритет.

```powershell
python tile_cache.py format x3d
python tile_cache.py format binary
python tile_cache.py info o3dt/v3/.../tile.o3dt
python tile_cache.py verify o3dt/v3/.../tile.o3dt
python tile_cache.py dump o3dt/v3/.../tile.o3dt --layer TREE --limit 30
python tile_cache.py dump o3dt/v3/.../tile.o3dt --layer ROAD --limit 10
python tile_cache.py dump o3dt/v3/.../tile.o3dt --layer MESH --index 1 --limit 12
python tile_cache.py extract o3dt/v3/.../tile.o3dt --index 1 --output mesh.bin
```

Python 3.9+, только стандартная библиотека. `info` показывает размеры разделов,
состав и геометрию; `verify` проверяет все разделы, CRC32, размеры и индексы;
`dump` переводит выбранные данные в JSON для анализа (`--limit 0` — все элементы);
`extract` выгружает **распакованный** раздел. `--index` — индекс в каталоге,
не номер меша. `format --root PATH` задаёт настройку другого корня кэша.
Эти `.md` и `.py` автоматически устанавливаются/обновляются в корне кэша
при создании карты. Исходники: `Osm3d/cache-tools/`; после правок разработчик
запускает `python embed.py` для обновления встроенной копии в приложениях.

## Общие правила

- Все числа little-endian, `u32/i32/u64/i64` — целые указанной разрядности,
  `f32/f64` — IEEE754. Никаких указателей, Pascal Boolean, padding или терминаторов.
- `string` = длина **в байтах** `u32`, затем UTF-8 без нулевого байта.
- Векторы — подряд X,Y,Z или X,Y (для карт это X,Z). Координаты локальные в метрах.
- Массив = явно указанное количество, затем плотные записи фиксированного размера.
  Переменные списки используют общие массивы точек/ширин и смещения в **элементах**.
- Сжатие zlib/DEFLATE, уровень записи 1. Если сжатие увеличивает раздел, он хранится
  без сжатия. Точность исходных чисел не меняется и не округляется до десятичных строк.
- Производные тени, GPU-буферы и прочие временные данные не сохраняются.
- Материалы и POI имеют имена перечислений, поэтому смена порядковых номеров
  перечислений не меняет смысл старого кэша. Тип дерева — существующий GPU type + 1;
  ноль означает старую запись без явно заданного процедурного типа.
- Игра проверяет каталог, размеры, CRC32 и индексы. Неисправный файл — промах кэша
  с возможностью чтения оставшегося X3D или повторного построения тайла.
- Лимиты v1: 65 536 разделов, 512 МиБ на распакованный раздел, 4 ГиБ на весь
  распакованный тайл, 1 МиБ на строку. Текущая реализация Pascal требует
  little-endian CPU; инструмент Python учитывает порядок байтов хоста.

## Заголовок — 32 байта

| Смещение | Тип | Значение |
|---:|---|---|
| 0 | 8 bytes | ASCII `O3DTBIN1` |
| 8 | u32 | версия 1 |
| 12 | u32 | маркер `0x01020304` |
| 16 | u32 | количество записей каталога |
| 20 | u32 | резерв 0 |
| 24 | u64 | смещение каталога, 32 |

Сразу далее каталог по 40 байт на раздел (`struct '<4sIQQQII'`):

| Поле | Тип | Смысл |
|---|---|---|
| kind | 4 bytes | `META`, `MESH`, `TREE`, `POIS`, `ROAD`, `BULD`, `MODL`, `MHOL` |
| flags | u32 | 0: без сжатия, 1: zlib |
| offset | u64 | абсолютное смещение данных |
| packed_size | u64 | размер в файле |
| raw_size | u64 | размер после распаковки |
| crc32 | u32 | CRC32 **распакованных** данных, совместим с `zlib.crc32` |
| reserved | u32 | 0 |

Разделы идут сразу за каталогом, непрерывно в порядке записей. `MESH` повторяется
для каждого меша. Остальные обязательные разделы присутствуют по одному, в том
числе с нулевым количеством элементов. Неизвестные дополнительные разделы
пропускаются читателем v1. При несовместимом изменении схемы нужна новая версия.

## META: метаданные

`zone:u32, north:u32 (0/1), tx:u32, ty:u32`, затем шесть `f64`:
`origin_lat, origin_lon, bbox_min_lat, bbox_min_lon, bbox_max_lat, bbox_max_lon`,
затем `generator_hash:string`. Фиксированная часть — 64 байта.
Пустая граница имеет служебное значение `(1e9, 1e9, -1e9, -1e9)`.

## MESH: геометрия

Необязательный слой `BCOL` хранит принятые цвета стен независимо от материала:
`version:u32 = 1`, `count:u32` (0..8192), затем `osm_id:i64, rgb:u32` по 12 байт.
ID уникальны и ненулевые; совпадают с OsmId геометрии здания. Цвет —
`0x00RRGGBB`. В текстовом кэше соответствует `O3DBuildingTints data="..."`
с массивом `{osm_id: string, color: "#RRGGBB"}`. Слой читается вместе с мешами,
при загрузке только дорог пропускается. Старые файлы без него сохраняют свой цвет.
Рендер объединяет цвета в палитру до 31 оттенка на композит (излишние сопоставляет
ближайшему); слот упакован в старший разряд seed, без нового атрибута вершины.

Необязательный слой `FACA` хранит принятую раскладку фасадов по фотографиям.
Он загружается вместе с `MESH`; загрузке только маршрута этот слой не нужен.
Старые файлы без `FACA` используют обычную процедурную раскладку.

Внутри `FACA`: `version:u32 = 1`, `count:u32` (1..4096), затем для каждого
фасада заголовок `<q4d6f2I` (72 байта): OSM ID, start lat/lon, end lat/lon,
локальные start X/Z и end X/Z, глубина балкона, ширина балкона в долях оконного
модуля, число модулей, число карнизов. Далее модули `<ffI>`: ширина в метрах,
сдвиг окна в долях этажа, битовая маска этажей балконов. Бит 0 запрещён,
биты 1..23 — этажи над первым наземным этажом. Последний массив — положения
карнизов `f32` в долях этажа, строго возрастающие. Не более 32 элементов
каждого массива. Повтор модулей начинается от start; наружная нормаль —
векторное произведение start→end на вертикаль. Это типизированные массивы,
а не вложенный JSON. В текстовом кэше им соответствует `O3DFacades` с
экранированным JSON в атрибуте `data`.

### Массивы MESH

`name:string, material_enum_name:string`, затем восемь `u32`:
`flags, vertex_count, pool_count, index_count, material_count, water_count,
osm_count, border_count`.

`flags & 1`: Solid (односторонняя геометрия), `flags & 2`: есть массив pool_indices.
Далее массивы **именно в этом порядке**:

| Массив | Элементы | Запись |
|---|---:|---|
| position_normal | pool_count | X,Y,Z,NX,NY,NZ: 6 × f32 = 24 байта |
| pool_indices | vertex_count, только при flags & 2 | u32 |
| UV | vertex_count | U,V: 2 × f32 |
| triangle_indices | index_count | u32; тройки индексов, без X3D-разделителя -1 |
| material_ids | material_count | i32 |
| water_scale | water_count | f32 |
| osm_ids | osm_count | i64 |
| border_indices | border_count | u32 |

Для вершины i берём позицию/нормаль из `position_normal[pool_indices[i]]` либо
`position_normal[i]`, если индексов пула нет. UV и дополнительные атрибуты
остаются индивидуальными. Пул используется у композита, объединяет только
**побитно одинаковые позиции и нормали** — не сглаживает рёбра и не округляет их.
Количество material/water/osm равно нулю или vertex_count. При отсутствии osm
его значения равны 0. Triangle/border indices адресуют итоговые вершины, не пул.

## TREE: деревья и кусты

`count:u32`, затем **один массив по 40 байт на экземпляр** (`'<6fIIii'`):
`x,y,z,scale,rotation,seed:f32`, `flags:u32` (bit 0 — куст),
`type_plus_one:u32`, `lat_e7:i32`, `lon_e7:i32`.
Поворот в радианах. E7 — широта/долгота × 10^7. Отдельных текстовых объектов нет.

## POIS: точки интереса

`kind_count:u32`, далее kind_count строк с именами перечисления TPOIKindExt.
Затем `count:u32` и массив по 20 байт (`'<I4f'`):
`kind_index:u32`, `x,y,z,rotation:f32`.
Далее опционально `count` значений `height:f32` (0 — стандартная высота модели,
0.3..20 — высота фонаря в метрах). Старые файлы без массива высот читаются с 0.
Типы фонарей дописаны в словарь POI; существующие типы и 20-байтовые записи не меняются.

## ROAD: оси дорог и параметры покрытия

Три `u32`: `segment_count, point_count, lane_width_count`.
Далее массив сегментов по **76 байт** (`'<IIfqIii3fiiiiifII'`):

| Поля в порядке записи | Типы |
|---|---|
| point0, point1 | 2 × u32 |
| width | f32 |
| way_id | i64 |
| flags (bit 0 — мост/туннель для привязки) | u32 |
| forward_lanes, backward_lanes | 2 × i32 |
| uv_min, uv_max, uv_scale | 3 × f32 |
| marked, surface, condition, both_ways, custom | 5 × i32 |
| edge | f32 |
| lane_offset, lane_count | 2 × u32 |

После записей: `point_count` пар X,Z (`2 × f32`), затем `lane_width_count`
значений ширины полос (`f32`). Сегмент адресует две точки и диапазон ширин,
lane_count ≤ 32. Surface: 0 неизвестно, 1 асфальт, 2 прочее, 3 бетон.
Condition: 0 не задано, 1 новое … 5 разрушенное. UVScale=0 — старый профиль.

## BULD: контуры зданий для обхода препятствий

`building_count:u32, point_count:u32`, затем building_count записей по 16 байт
(`'<ffII'`): `base_y:f32, max_y:f32, first_point:u32, point_count:u32`.
Затем общий массив пар X,Z (`2 × f32`). Y контура не используется и восстанавливается
нулём, границы AABB вычисляются заново. TileKey — временный владелец в индексе,
в файл не записывается.

## MODL: внешние GLB/X3D

`file_count:u32`, далее file_count строк — относительные имена ресурсов.
Затем `count:u32` и массив по 44 байта (`'<I10f'`): `file_index:u32`,
`position:3f32, rotation:4f32 (ось XYZ + угол), scale:3f32`.
Файлы моделей не встраиваются в кэш; путь трактуется так же, как в X3D.

## MHOL: люки

`count:u32`, затем массив по 32 байта (`'<7fi'`):
`position:3f32, normal:3f32, rotation:f32, kind:i32` (0…8).

## Частичное чтение и кэш маршрута

Для дорог читаются только каталог + META + ROAD. Для препятствий — META + BULD.
Меши, растительность и модели при этом не распаковываются. Для проверки кэша
притягивания достаточно CRC32 и размеров META/ROAD из каталога; полное чтение
дорог всё равно проверяет их CRC. Изменение геометрии без изменения осей дорог
не заставляет повторно притягивать маршрут. Подготовка обхода зданий использует
актуальный BULD отдельно. Пространство кэша привязки — `route-snap-v7`.
